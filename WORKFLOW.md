## 1. Establish the program population

Build a register of historical OR/OM/IE doctoral programs. Operations Academia is a discovery source, not proof of degree provision or a complete historical frame. Add official catalogs and archives, dissertation repositories, predecessor departments and closed programs. Distinguish university, school, department, program, specialization and campus. A department merger does not establish a degree's closure date.

Public register: `data/doctoral-programs.json`. Every non-null fact has source IDs and `lastCheckedAt`. Dates of first intake, admission cessation, closure and last degree award are separate. Partial field eligibility and historical non-PhD credentials remain explicit. The initial register is only a pilot; its size must not be described as the worldwide program total.

## 2. Enumerate graduates before selecting careers

Work program by program and graduation year by graduation year. Reconcile official graduate rosters, dissertation records, commencement lists and alumni reports. Distinguish candidacy, defense, submission and awarded degree. Keep the actual degree title and specialization evidence. Link to existing people only after identity review.

For each program-year, record known official total, identified names, degree verification, missing names, source coverage and reconciliation status. A complete outcome list is not evidence of a complete graduate roster. People entering industry immediately must enter through these rosters, not through faculty directories.

Graduate lists from program pages (started 18 October 2026): `research/graduate-list-pages.json` lists the placement, alumni and graduate pages cited in first-job reviews (add pages by hand with the institution name as the data writes it). `node scripts/collect-graduate-lists.mjs snapshots` lists one archived snapshot per calendar year for each page (the Internet Archive's CDX index, or its availability service year by year when `web.archive.org` is refused); `fetch` saves the live page and each snapshot as text under `research/graduates/snapshots/<key>/` (ignored); `chunks` writes `research/graduates/chunk-N.json` with the texts not yet extracted. Extraction agents (brief: copy, never infer; one record per person, page and snapshot; the year's meaning as the page gives it) write `research/graduates/proposal-N.json`; `node scripts/merge-graduate-lists.mjs research/graduates/proposal-N.json` validates them and rebuilds `data/graduate-lists.json` (one record per person, institution and listed year, every snapshot kept as a sighting, a link to the people database only when name and PhD institution both match, a name match elsewhere kept as a lead) and records the extracted files in `research/graduates/extracted.json`; each merge also recomputes every record's field (operations, another field, unstated) from its sightings, and `node scripts/merge-graduate-lists.mjs --refield` does only that after a change to the area rule. A page the address filter skips but a lookup captured (IIM Kozhikode's student-thesis page) enters through an integrator review file (`commoncrawl/review-N.json` with `reviewer: integrator`), then `accept`, `candidates`, `fetch --page <url>` and `collect-graduate-lists.mjs chunks`. Rerun `snapshots` and `fetch` to pick up new years; no program-year is ever marked complete from these pages alone. A second archive, Common Crawl (`python3 scripts/commoncrawl-graduate-pages.py`, state under the ignored `research/graduates/commoncrawl/`): `scan --per-year 2` streams each chosen crawl's index (2013 onwards; `--all` for every crawl, `--crawl ID ...` for named ones), reads the index chunks that cover the institutions' hosts (`research/graduates/domains.json`) and keeps captures whose address names a placement, job-market, dissertation, alumni or graduates page in a business, operations or engineering setting (`hits-<crawl>.jsonl`, `scanned.json` with the chunks the data server refused); `candidates` groups the hits by address into `candidates.json` and the review sheet `candidates.md` (known pages marked; per-person pages folded under their list page); `peek` saves the latest capture of each new candidate as text under `peek/`; `review-chunks` batches them into `review-chunk-N.json` for review agents, who write `review-N.json` (`{"pages": [{url, institution, scope, reason, reviewedAt}]}`, scope `program-list`, `single-record` or `not-a-list`); `accept` adds the reviewed pages to `research/graduate-list-pages.json`; `fetch` saves one capture per calendar year of every in-scope page into the same `snapshots/<key>/` layout (registered in `plan.json` as `via: commoncrawl`), so `chunks`, the extraction agents and the merge run unchanged. A Common Crawl capture's source URL is the public index lookup for that address and crawl (`https://index.commoncrawl.org/<crawl>-index?url=...&output=json`); the text footer names the WARC file, offset and length, and the merge labels each sighting `live`, `internet-archive` or `commoncrawl`. The data server allows a few parallel range requests; the scan uses two paced readers and retries refused chunks slowly (more readers make it refuse most chunks). `lookup --prefix <address prefix> ... (--all | --crawl ID ...)` reads only the index chunks that cover the named address prefixes across the chosen crawls and writes `lookup-<crawl>.jsonl` (with `lookup-done.json`), for leads whose address is known but which the address filter or the sampled crawls missed (cohort pages, per-department thesis databases, renamed placement pages); `candidates` reads the lookup hits with the scan hits. A page whose list is drawn by scripts (the plain copy holds only navigation, as for Alberta's graduates table and Vienna's prior placements) is read live in headless Chromium (Playwright with `executablePath: '/opt/pw-browsers/chromium'`), every table page included, and saved as `snapshots/<key>/live.txt` with a footer naming the page address and `via headless Chromium`; add the page to `research/graduate-list-pages.json` and an entry to `research/graduates/plan.json` under the same key the scripts derive from the address, then run `chunks` as usual. A page marked `readOnce` in the page list (an undated catalogue, a single profile, a page that lists everything on every capture) is read in its latest capture only; `single-record` pages behave the same way.

## 3. Research a person

Open the public profile/CV and relevant institutional sources. Record degree, advisors, each dated employment period and publication metadata as separate facts. Preserve concurrent roles, missing dates and conflicting evidence. Identify the first new job only after checking for postdocs, visits and industry employment. Record later sector changes without treating every consultancy or adjunct role as a primary-job transition.

For publications, distinguish journal articles, conference papers, preprints and accepted work. Link versions and disambiguate authors. Default snapshot: publications through the end of the PhD calendar year. Separately assess publication by the actual degree date when chronology allows. Do not reconstruct historical citations from today's citation counts.

## 4. Submit a first-job proposal

The current merger accepts an array (or `records`/`results` array) of records with:

| Field | Requirement |
|---|---|
| `facultyId`, `name` | Exact existing ID and imported name |
| `status` | `verified`, `unresolved` or `not-yet-completed-phd` |
| `checkedAt`, `reason` | Date and substantive review explanation |
| `sources` | Nonempty list of `{url, title, notes}` for opened/attempted evidence; failures described honestly |
| `employer`, `evidenceUrl`, `evidenceNote` | Required for verified first employment; primary URL must be in sources |
| `position`, `placementYear` | Explicitly known value or null |
| `category` | `tenure-track`, `postdoc`, `other-academic`, `industry`, `government`, `nonprofit` or `unknown` |
| `phdYearVerified`, `phdInstitutionVerified` | Independently supported value or null; do not copy directory values and call them verified |
| `phdYearResolution`, `phdInstitutionResolution` | Required explanation when correcting an imported value |

The current `category` is a legacy placement display field. The relational schema separates sector and appointment type: a corporate postdoc can be industry and postdoc simultaneously. Do not lose that distinction in expanded career data.

Record dates (added 18 October 2026): every record in the fourteen databases (`faculty`, `faculty-roster-people`, `faculty-rosters`, `placements`, `research-status`, `universities`, `institutions`, `entities`, `employers`, `doctoral-programs`, `graduate-lists` and the three location files) carries `addedAt` (first published) and `updatedAt` (last content change), both UTC date-times. `node scripts/record-dates.mjs` stamps them from the ledger `data/record-dates.json` (one entry per record: the two dates and a hash of the record without them, so a rebuild that leaves a record unchanged keeps its dates); `update-research-status.mjs` runs it at the end, so run the status update last, after every merge or rebuild, and `npm run check` (`record-dates.mjs --check`) refuses a record whose stamp is missing or stale. For a person, `updatedAt` also moves when their first-job record or research disposition changes. Dates before 18 October 2026 13:00 UTC were reconstructed from the Git history of each file (`node scripts/record-dates.mjs --backfill`: the committer time of the first commit that contained the record and of the last that changed it); later ones are the time of the integration. ## 7. Keep the documentation current

Only edit files affected by new information. Future agents should follow this maintenance step without needing a separate reminder. It does not imply an automatic scheduled update service.
